# 存储约束

M0不创建业务数据库。后续存储实现采用better-sqlite3与Drizzle，SQLite中的durable events是Session执行事实的唯一持久来源；JSONL用于显式导入导出，不参与实时双写或恢复来源选择。

- SQLite保存Workspace、配置、记忆、看板以及Session/Run/工具/审批等执行事件；事件有明确关联、顺序和事务提交规则，恢复与审计从已提交事件重建。
- 进程中的Agent、连接、锁和队列是临时状态；需要重启恢复的事实不能只放Map/Set。
- FTS、向量和目录缓存是派生索引，必须可由原始事实重建。
- 使用显式版本化迁移，随应用发布和执行；已发布迁移冻结，只追加后继迁移，不编辑旧文件改变已有安装。
- 数据转换、备份与失败恢复步骤在迁移Spec写清楚；不能沿用远端MySQL手工DDL政策替代本机升级流程。
- JSONL导出从已提交SQLite事件生成；导入先验证完整记录、格式版本、关联和顺序，再按明确事务规则写入，不静默丢弃损坏内容或覆盖已有会话。
- 先持久化事实再更新派生索引；索引失败不能删除已经保存的事实。
- 凭据与普通业务数据分别管理；数据库Entity与凭据对象不作为跨端DTO。

没有实际迁移和恢复检查时不声明支持已有用户数据升级。

## 数据与事务

数据库连接和写入由daemon的存储模块拥有，Renderer和main不直接打开同一业务数据库。按实际领域拆repository，公开DTO显式选择字段；不能将Drizzle查询结果自动视为协议响应。

主键与外部ID稳定且不包含磁盘路径，选型在领域schema中确定，不机械添加所有Magic Book审计字段、t\_前缀或软删除。删除与保留政策由数据所属功能规定，不以软删除代替真实隐私删除要求。

Session事件具有sessionId、唯一eventId、单会话递增seq、事件类型与格式版本；具体字段由后续协议决定。唯一约束和事务保证顺序，不能用Date.now单独承担排序或幂等。Run结束、工具结果与相关事实需要一起可见时在同一事务提交；状态投影和索引可重建，不能先向客户端广播尚未提交的完成事实。

事务范围只含本机数据库操作，不在SQLite事务中等待模型、HTTP或用户审批。同步better-sqlite3调用限制批量规模；数据库锁竞争与busy错误明确处理，不能无限重试。SQLite是本机数据，不将WAL数据库放网络共享目录充当多人数据库。[SQLite WAL](https://sqlite.org/wal.html)

索引覆盖实际关联和查询，避免循环N+1、无界全表加载及SQL字符串拼接；按参数绑定输入。大列表分页，批量导入限制内存，状态与事件的写入原子性由事务承担。[SQLite原子提交](https://sqlite.org/atomiccommit.html)

## 迁移与备份

迁移按单调版本运行，启动业务前检查已应用版本；未知更高版本明确拒绝，不尝试降级。迁移文件、校验信息和实际应用版本一同发布，已有安装不能依赖用户手工运行DDL。

每个迁移说明前置版本、数据转换、预计工作量、失败处理和验收用例。破坏性改变先定义可恢复备份和保留策略，备份检查可打开、版本可识别且能恢复；已发布迁移只追加，开发未发布迁移允许在任务范围内修订。

运行中数据库备份使用SQLite备份API或停写后完整快照，不只复制一个.db忽略活动WAL。恢复先检查格式、完整性和目标版本，再替换数据；损坏数据库不能静默重建空库并显示成功。[SQLite备份API](https://sqlite.org/backup.html)

## 导入、派生索引与恢复

JSONL是可交换数据。导入定义重复会话/事件的拒绝或显式合并规则、版本升级步骤和事务范围；读取中途失败不能留下被标记完整的会话。导出标注格式版本与范围，不能混入未提交状态、Token或内部临时对象。

记忆原文和来源是事实，FTS/vector是派生数据。embedding保存模型、版本、维度和对应原文版本；模型或维度改变重新构建匹配索引，不能混用不兼容向量。后台索引失败单独显示，不丢原文；持久事件与JSONL没有实时双写竞争。

进程重启从已提交事件区分正常完成、未完成与结果未知；不能将最后一条started自动推断为未发生副作用。恢复、重试和undo有明确作用范围与证据；外部副作用没有逆操作时不能宣称完全撤销。验证至少覆盖旧版本升级、损坏输入、事务中断与索引重建，具体用例属于功能Spec。
