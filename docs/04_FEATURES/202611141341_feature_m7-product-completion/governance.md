# M7 代码治理

## Spec

2026-11-14按用户要求复核当前未提交的M7实现，属于M7交付前治理，不扩展里程碑。治理依据为[代码规范](../../10_GOVERNANCE/code.md)、[服务端](../../10_GOVERNANCE/server.md)、[Web](../../10_GOVERNANCE/web.md)及[桌面](../../10_GOVERNANCE/desktop.md)检查项。

### Intent

确认请求观察、用量、原生文件发布与归档恢复各有明确拥有者；清理已被后续实现替代的代码、重复可写状态和无消费者出口，并复核取消、关闭、权限和持久恢复的实际行为。

### Constraints

- 保留现有M7及其他工作树改动，不回退功能、不修改真实用户profile、会话、工作区或凭据，不启动付费请求。
- 先核对生产、测试、构建、动态注册和发布入口，再判断代码是否无效。不以减少文件数量、单纯行数或机械抽象为目标。
- 不重做消息体系，不改变任务预算策略，不借治理扩大办公生成、平台或发布验收范围。
- 已通过且源码未变化的检查保留原证据；修复建立有意义的回归，再执行受影响检查及必要静态门禁。不自动提交或推送。

### Acceptance Criteria

1. 请求、Usage、文件发布、归档发布和Renderer状态的拥有者及消费者已核对，明确问题与保留项分别说明。
2. 发现的真实缺陷、重复实现或无效出口在所属模块修复；取消、幂等、错误及资源回收语义有相应验证。
3. 已实现能力的文档使用当前状态，规划基线和未验范围有明确说明，不保留与实际API矛盾的承诺。
4. 交付记录只列实际命令、结果、修复与未验项，不将上轮检查或安装包当作本轮新变更已验证。

## UseCase

审阅一个M7请求、文件操作或归档任务时，可以从入口找到唯一执行/持久拥有者；失败或取消后资源有明确收口。维护者可以区分仍有消费者的接口、已被替代的实现，以及当前工作树和已有验证产物。

### 保留的设计

- 请求dispatch与辅助模型scheduledStream分别拥有重投影和调度收口，观察器复用同一流/result；不为相似代码强行合并不同职责。
- 文件发布、归档发布、Trace投影和用量聚合仍各有一个拥有者；传输层限制比存储层更严格属于各自入口约束，不合并为通用配置对象。
- 源码、测试、动态资源、构建及exports消费者核对后，未发现需要整模块删除的重复实现，不以静态一次未命中裁剪公开出口。
- electron-builder当前固定版本会在复制Windows额外资源时签名；最初的漏签疑点经依赖实现核对已排除，不为此新增第二套签名流程。
- Web全局已经禁用focus/reconnect自动重读，无需叠加额外设置；冻结页仍支持手动重试、重新打开和明确分页读取。
