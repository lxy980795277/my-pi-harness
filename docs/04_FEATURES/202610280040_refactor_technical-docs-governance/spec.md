# 技术专题拆分与全仓治理

## Spec

### Roadmap Alignment

本轮属于M0工程维护、M4插件与MCP技术沉淀及M1–M4存量治理，沿用[roadmap](../../00_OVERVIEW/roadmap.md)现有范围。M5尚未开始，真实账号、Office视觉和Windows验收缺口保持原状态。

### Intent

将插件体系和MCP连接分别整理为当前实现的技术文档；旧能力扩展文档被新专题完整承接后移除。按docs/10的代码、Renderer、daemon与桌面治理清单检查存量代码，清理有证据的缺陷、重复事实和无消费者内容。

### Constraints

- 以本仓库实现为依据，技术设计只记录当前职责、关键流程、失败及边界，不复制参考项目代码或维护第二份协议。
- 安装、插件账号授权、MCP启动信任、Run能力冻结与逐次工具审批分别描述；保留Skills、只读网关、办公资源和动态加载的说明归属。
- 不为扫描结果机械删掉动态入口、资源、schema、公开导出或规划资产，不扩张功能，不改变数据格式或清理用户数据。
- 用户已授权文档调整、治理修复和后续本地提交，按提交流程同步0.10.1版本与发布记录；不push，不扩大功能范围。

### Acceptance Criteria

- AC1：09中存在插件体系、MCP连接两篇独立技术文档，源码锚点与当前实现一致，覆盖状态来源、授权、调用、资源回收与当前限制。
- AC2：旧专题中仍有效的独立内容有明确新归属，删除旧文件并同步所有链接，无死链与同一事实的竞争说明。
- AC3：按10的四类清单完成审查，按实际风险记录位置、触发、证据、修复和验证，区分已修复项、无问题范围和未验证平台。
- AC4：有证据的修复保持既有行为或有明确回归用例，静态、类型和定向行为检查通过；检查选择与实际结果写入verify。

## UseCase

- UC1：维护者从技术总览进入插件专题，能追踪manifest、安装组件、OAuth、Skill网关与按需工具的状态来源；非插件MCP差异通过链接进入独立专题。
- UC2：维护者调查MCP连接失败，能定位stdio/HTTP/SSE、秘密、独立OAuth、目录预热、冻结、租约、取消及unknown语义；不会把插件授权等同于全局MCP信任。
- UC3：按治理清单检查各层，真实问题修复后运行覆盖主路径、拒绝或竞态的检查；无足够删除证据的代码保留，未执行的视觉/账号/平台验收标为未验证。
