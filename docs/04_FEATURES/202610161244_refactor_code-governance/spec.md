# 代码治理与可读性

## Spec

状态：2026-10-16设计、治理和自动化验证完成，见[验证记录](verify.md)；保留工作区已有未提交M3改动，不提交、不推送，不改变业务功能或数据。

### Roadmap Alignment

本轮属于M0工程范式及M1–M3存量代码治理，不进入M4，也不改写M2平台暂缓项。共用规则由docs/10_GOVERNANCE/code.md拥有，前后端规范和入口链接引用。

### Intent

统一领域类型文件命名，减少散落的业务状态字面量和已弃用API，让多源选择、错误优先级及空值处理可以直接阅读；将死代码检查扩展为持续代码治理。

### Constraints

- 将types目录的workspace-view.ts等冗余后缀文件改为workspace.ts等领域名，并同步全部消费者；不机械改掉明确区分公开投影与宿主实体的类型名称。
- 业务枚举值使用所属types模块内具名联合类型，优先派生已有协议类型。Hook签名、状态和复杂属性不重复长字面量；不要求改为运行时enum，不另建第二份协议/schema事实。
- 按已安装依赖类型的deprecated声明识别弃用使用，替换真实推荐API；React表单提交使用SubmitEvent/SubmitEventHandler，不把FormEvent换成同样弃用的FormEventHandler。加入类型感知no-deprecated检查与真实合法/非法用例。
- 空值逻辑优先可读性。展开多级??、可选链叠加查找和多来源错误选择；简单明确默认值、稳定selector常量及??=生命周期缓存可保留。不把??换成||，必须保留0、false、空字符串及null/undefined语义；不新增通用fallback工具掩盖业务分支。
- 继续使用shadcn、Hook/TSX分工及既有导入/异步规则。重构不改变权限、协议、持久格式、消息发送、压缩/审核/恢复或UI交互。
- 不删除有实际入口的资源、依赖、导出或已有M3改动；识别死代码需核对动态注册、CSS、schema、测试及产物。

### Acceptance Criteria

- AC-01：types目录冗余\*-view文件名清理，旧路径无剩余消费者，Web各编译面通过。
- AC-02：点名的checkpoint确认类型及其他重复业务联合使用具名类型，来源明确；不复制协议联合或用断言掩盖类型错误。
- AC-03：已弃用的实际API使用清理，typed ESLint可拒绝回归，fixture同时证明替代API通过。
- AC-04：use-compactions及其他复杂空值/错误优先级表达式使用明确变量和分支；现有0/false/空字符串行为保持。
- AC-05：dead-code.md重命名code.md，原死代码/依赖/导出规则与本轮原则合并精简；全仓链接有效，不扩增05规范数量。
- AC-06：定向行为、lint、类型与必要浏览器回归通过；验证记录区分本轮与已有M3证据。

## UseCase

- UC-01 阅读工作区/会话/上下文类型与Hook，文件名直接表达领域，状态联合有单一可引用名字。
- UC-02 在摘要列表为空、当前摘要存在、选择历史摘要或找不到所选ID时，明确按当前摘要/最新版本选择，行为保持。
- UC-03 提交新对话、问答、计划或工作区表单，使用当前React提交事件；键盘发送、取消和异步处理不改变。
- UC-04 在多源错误同时存在、配置未加载或值为0/false/空字符串时，按原优先级显示/选择，不能因重构更改有效值。
- UC-05 新增弃用类型或types/\*-view.ts时，实际规则拒绝；合法类型文件和非弃用API通过。未引用资源仍先查真实消费者再删除。
