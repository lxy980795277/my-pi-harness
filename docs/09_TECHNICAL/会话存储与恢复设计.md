# 会话持久化与恢复设计

**日期**：2026-10-16

**模块**：`packages/storage`、`packages/agent-runtime`、`apps/daemon`

**实现锚点**：`ProfileStore`、`SessionJournal`、`AttachmentBlobs`、`ProjectionWriter`、`SessionRuntime.commit`

**状态**：已实现；本机自动化证据见 [M3 验证](../04_FEATURES/202610151655_feature_m3-context-interaction/verify.md)，目标平台限制见本文。

---

## 要解决什么问题

Agent 的持久数据既有页面需要的文本，也有继续调用模型所需的消息 codec、工具结果、冻结请求、队列来源和分支关系。只保存聊天文本，重启后就无法可靠区分“没有执行”“已经执行”和“结果未知”，也无法复原正确的模型上下文。

这里需要同时解决四个问题：

1. **执行事实完整落盘**：接受请求、消耗队列和创建用户消息必须整体保存，不能只保留对外事件。
2. **查询方便且能够重建**：页面需要会话列表、分支消息、工作状态和事件分页，不能每次查询都遍历所有日志。
3. **崩溃后不重复副作用**：文件和 SQLite 无法组成一个跨介质事务，写入失败时必须准确处理已提交和结果未知的状态。
4. **恢复保留真实历史**：摘要、分支、人工问题和检查点恢复都需要保留原始事实，不覆盖旧消息或重跑工具。

**核心思路**：每个 Session 的 JSONL 保存完整执行事实；不可变附件文件保存冻结内容；SQLite 保存配置事实及可重建会话投影。提交顺序固定为“整批校验 → JSONL 追加并 fsync → SQLite 提交 → 发布公开事件”。

**核心特点**：

- 一行 JSONL 对应一个完整命令批，批内事件整体回放。
- 宿主恢复材料与公开事件共存于日志，但对外查询显式过滤私有字段。
- 启动持有 profile 排他锁，从附件文件和日志重建投影，再追加中断事实。
- 日志写入或索引提交发生不确定失败后冻结持久写入，等待修复和重启。

## 一、整体架构

```text
SessionRuntime / WorkRuntime / ToolRuntime
  │ 完整命令事件批，含宿主 privateData
  ▼
ProfileStore
  │
  ├─ SQLite 短事务：校验关联、状态、revision，应用待提交投影
  │
  ├─ SessionJournal.append()
  │    └─ <sessionId>.jsonl：完整批记录 → fsync
  │
  └─ SQLite COMMIT
       ├─ 会话、消息、Run、队列、分支、工作状态、事件查询投影
       └─ 返回已提交公开事件
            │
            ▼
       SessionRuntime.publish() → HTTP/SSE → Web

AttachmentService → AttachmentBlobs
  └─ 冻结内容 → 临时文件 fsync → 排他发布 → 同步目录
       └─ SQLite 附件元数据索引
```

存储包拥有磁盘和数据库事务；运行时通过端口提交事实，不直接操作 SQL。模型调度、取消和队列执行由 [Agent 运行时](Agent-Runtime.md) 解释；请求上下文和摘要由 [上下文管理](上下文管理设计.md) 解释。

## 二、数据由谁拥有

| 数据                                 | 权威来源             | SQLite 中的用途              |
| ------------------------------------ | -------------------- | ---------------------------- |
| 会话创建、配置修改、归档             | Session JSONL        | 列表和当前配置投影           |
| 消息、Run、工具及审批事实            | Session JSONL        | 消息呈现、执行状态和工具排序 |
| 请求幂等、队列、分支关系             | Session JSONL        | 请求结果和待消费输入查询     |
| 分支工作状态、摘要版本、检查点       | Session JSONL        | 当前状态和版本列表           |
| 模型 codec、冻结请求、工具结果 codec | JSONL `privateData`  | 宿主恢复投影                 |
| 附件冻结文本、图片和元数据           | 校验和保护的附件文件 | 可重建元数据索引             |
| Provider、工作区、应用设置           | SQLite               | 配置事实，不能从会话日志重建 |
| API Key、OAuth Token                 | 系统凭据库           | 仅保存凭据引用和非秘密元数据 |

“会话投影可重建”不代表可以直接删除整个 SQLite。配置表仍是独立事实；完整备份还需要日志、附件和对应配置。活动数据库的备份需要考虑 WAL，不能只复制 `data.sqlite` 主文件。

### 2.1 公开投影与私有材料

`HarnessEvent` 包含页面能够消费的事件；同一条磁盘记录还可以保存 `privateData`。后者包括模型原始消息 codec、工具结果和请求参数，不能直接作为 SSE 内容。

`readEvents()` 显式选择公开 envelope 字段；`getSnapshot()` 返回协议声明的投影。模型历史由 `getModelContext()` 读取私有 codec，按分支消息顺序插入配对工具结果，缺失必要 codec 时明确失败。

JSONL 是宿主私有数据，不是脱敏导出格式。用户正文、工具结果和冻结上下文可能包含敏感信息；图片内容通过受保护附件接口按需读取，不进入公开消息快照。

会话顶部的日志下载是用户明确触发的原始文件导出，复用业务登录和profile归属校验。storage固定当前已提交的文件前缀并从该文件描述符流式读取，完整保留全部分支的批记录；运行中的后续追加不改变已开始的下载。接口及错误语义见[会话协议](../03_API/model-session.md#事件快照与断线)，附件和配置继续独立保存。

## 三、目录与 profile 隔离

应用启动入口将日志根确定为仓库根目录的 `.my-pi-harness`。这一规则同时适用于开发入口、仓库内源码和构建后 daemon，不随启动命令的 cwd 或 profile 覆盖而改变。

```text
<repository>/.my-pi-harness/
  sessions/
    <SHA256(canonicalProfilePath)>/
      <sessionId>.jsonl
      attachments/
        <attachmentId>.json

<profileDirectory>/
  owner.sqlite
  data.sqlite
  data.sqlite-wal / data.sqlite-shm（SQLite 运行时文件）
```

profile 是数据库配置和凭据命名空间，与工作区目录、日志根相互独立。不同 profile 即使共享日志根、使用相同 Session ID，也因 canonical profile 路径摘要而分开保存。

独立安装包脱离源码仓库后不能推断用户选择的仓库位置，必须通过 `MY_PI_HARNESS_SESSION_LOG_ROOT` 指向该仓库中的隐藏目录；未指定则启动失败。所有启动参数和 profile 默认位置由 [架构启动配置](../01_ARCHITECTURE/overview.md#启动配置) 维护。

storage 库本身不读取 cwd 或 `NODE_ENV`；低层调用省略 `sessionLogRoot` 时使用 profile 内的隐藏根。产品启动始终显式传入上述仓库根，测试显式使用临时根，不把低层默认值当成产品路径规则。

### 3.1 文件保护

`PrivateSessionFiles` 检查根目录、profile 命名空间和附件目录的真实身份；POSIX 上持有目录 fd，目录使用 `0700`、文件使用 `0600`。ID 先校验为允许的文件名，再拼接路径。

读写拒绝符号链接、非普通文件、多硬链接、非当前用户拥有的数据和目录替换。追加日志还比较上次保存的文件身份、大小和修改签名，发现运行时被外部更改后拒绝继续追加。

日志目录不能注册为工作区；父项目仍可注册，普通文件工具和沙箱 Shell 排除 `.my-pi-harness`。用户选择的 `.workspace` 是普通工作目录，不因名字以点开头而被排除。

## 四、命令如何成为完整事实

### 4.1 批次格式

每行 `SessionBatch` 保存格式版本、`batchId`、`previousBatchId`、`sessionId`、`firstSeq`、`records` 和 SHA-256 校验和；每个 record 保存公开事件及可空的 `privateData`。

批次链和事件顺序共同校验：

- 当前批引用上一批 ID。
- `firstSeq` 等于上一个事件序号加一。
- 批内事件属于同一 Session，`seq` 连续递增。
- 结构、版本、UTF-8 和 checksum 均有效。

事件 ID 的唯一性还受投影数据库约束。单行当前限制为 32 MiB、最多 10000 个事件；日志读取按块处理，不一次读取整份会话文件。

### 4.2 提交时序

```text
运行时                    ProfileStore                JSONL              SQLite
  │ append(events)             │                        │                   │
  ├───────────────────────────►│ BEGIN IMMEDIATE         │                   │
  │                            ├─校验并应用整批暂存投影────────────────────►│
  │                            │                        │                   │
  │                            ├─追加一行完整批────────►│                   │
  │                            │                        ├─fsync             │
  │                            │◄───────────────────────┤                   │
  │                            ├─COMMIT────────────────────────────────────►│
  │◄─返回公开事件───────────────┤                        │                   │
  └─publish / SSE              │                        │                   │
```

整批校验在 SQLite 事务内进行。任一后续事件无效，前面应用的暂存投影回滚，JSONL 尚未写入；嵌套操作由最外层事务统一追加日志。

事务只属于一个 Session，不在其中等待模型、网络或用户。创建会话及初始工作状态可以在同一批提交；跨会话恢复分别提交，不能把多个 Session 混进同一行日志。

### 4.3 队列与幂等

`run.accepted` 和 `queue.added` 保存 request ID；请求接受结果独立投影，因此队列被消费或删除后仍能识别重复请求，返回原接受结果。

`queue.consumed` 必须与对应用户消息在同批提交。否则“输入已从队列消失、却没有成为消息”的状态无法恢复，存储会拒绝整个命令。队列来源从原始接受事件及 Run 解析，编辑文本不改变其接受分支。

当前 Run 的 steer 消费也遵守同一规则；持久化队列和 Pi 内存队列职责不同，后者只是活动执行的调度视图。

## 五、失败后如何处理

JSONL 和 SQLite 没有跨介质原子事务。应用采用明确提交顺序与失败冻结，避免把不确定结果当作可以安全重试。

| 失败位置                     | 已知状态                      | 当前实例的行为                   |
| ---------------------------- | ----------------------------- | -------------------------------- |
| 事件业务校验                 | 日志未写，事务回滚            | 拒绝命令，可修正输入后再提交     |
| 日志写入或 fsync             | SQLite 回滚，日志提交可能未知 | 冻结后续持久写入，要求修复并重启 |
| 日志成功，SQLite 提交失败    | 日志已提交，索引未可靠提交    | 冻结写入，重启从日志恢复         |
| 附件发布失败或发布后索引失败 | 附件结果可能未知或已提交      | 冻结写入，避免重复覆盖           |

冻结由 `ProfileStore.writeFailure` 保存，配置写入也受影响；存储层仍允许读取已有投影。运行时会停止受影响执行并禁用该 Session 的正常操作，不能继续展示一个看似健康的活动 Run。

错误响应不意味着磁盘操作一定没发生。尤其 JSONL 已提交时，不能根据客户端失败重复接受请求或重执行工具；重启回放只恢复事实，不执行模型或副作用。

## 六、启动恢复

### 6.1 先拥有，再恢复

`openProfileStore()` 先获得 profile 下 `owner.sqlite` 的独立排他事务，再校验 schema、打开数据目录和重建投影。第二个 daemon 使用同一 profile 会明确失败；进程死亡后的锁由 OS 释放，不按 PID 或时间猜测陈旧锁。

`data.sqlite` 使用 WAL 与 FULL 同步；锁库不删除，避免另一进程锁住不同 inode。构造或恢复失败必须关闭文件、数据库并释放所有权。

### 6.2 重建顺序

```text
获得 profile 锁
  → 校验当前 fresh schema
  → 枚举附件与 Session 日志
  → 检查已有索引引用的日志未丢失
  → SQLite 事务内清空会话派生表和附件索引
  → 校验附件文件，重建附件元数据
  → 按 Session 批次顺序投影完整日志
  → 校验消息和待消费队列引用的附件
  → 提交投影
  → 按 Session 追加 interrupted 事实
  → 对外提供服务
```

Provider、工作区和应用设置不参与清空重建。已有索引对应的日志缺失，或重建后该会话没有有效创建记录时明确失败；首次发现的空日志不会生成会话，也不因此报错。SQLite不会反向生成、覆盖或补齐权威日志。

### 6.3 只修复不完整末行

最后一个 JSON 片段不完整时，截断到上一完整行；最后一条结构完整、内容合法但缺换行的批次会保留并补换行。

中间坏行、完整但校验失败的末行、未知版本、断序或冲突不能自动跳过。读取失败保留问题现场并拒绝启动，不能让部分历史悄悄消失。

### 6.4 中断不等于回滚

旧活动 Run、未结束工具、待答问题和待审核计划转为 `interrupted`，通过追加事实完成；部分文本和队列保留，已有终态不改写。

恢复不自动继续模型请求、不重新执行工具、不沿用内存中的审批或问题等待。工具中断只说明缺少可靠终态，文件、Shell 或外部请求可能已经产生效果，后续重试应先检查实际状态。

## 七、附件、分支与检查点

### 7.1 附件不可变

附件先保存为带版本和 checksum 的文件：临时文件写完并 fsync，使用排他链接发布目标，再同步目录。相同附件 ID 不允许覆盖；残留临时文件不参与恢复。

SQLite 只保存附件元数据，读取内容时重新核查文件、schema、ID 和 hash。消息及队列引用的附件缺失或损坏时拒绝恢复，不能以空正文继续模型请求。

这里冻结的是 `AttachmentContent` 声明的文本、图片和元数据；不承诺额外保留所有原始文档二进制。未被消息引用的附件仍可能已持久化，当前没有自动回收承诺。

### 7.2 分支保留原历史

编辑并重发创建新分支，继承编辑点之前的消息前缀；旧分支和原消息保留。分支消息通过有序引用维护，历史 codec 按相同顺序重建，不靠消息创建时间猜测排列。

`work.updated` 保存 revision 递增的完整分支工作状态。上下文锚点必须属于分支；问题必须指向同 Session、同分支 Run；摘要版本 ID 不允许被改写，父版本须已存在。

### 7.3 两类恢复锚点

上下文压缩保存不可变摘要版本，选择版本影响后续请求上下文；手动检查点保存消息前缀和工作状态，恢复时创建新分支并提交分支选择及工作状态。

检查点不能在活动 Run 中创建或恢复。恢复清除待答问题和旧 usage，原分支仍在；它只恢复会话状态，不撤销磁盘、Shell 或外部系统。两类锚点的使用流程见 [上下文管理](上下文管理设计.md)。

## 九、边界与取舍

- 当前是开发期 fresh schema，不承担旧日志、旧 SQLite 或模型 codec 兼容；未知格式仍必须明确拒绝。
- 单 profile 由单 daemon 写入，仅支持本机文件系统，不提供共享网络盘多机写入。
- 日志按命令追加，流式增量也会落盘；同步 fsync 与启动全量重建换取当前明确的恢复机制，未来优化需要保持同一事实顺序。
- 文件身份检查不能提供针对同用户恶意进程的完整隔离；Windows 目录 fd、ACL 与目录持久化语义仍需真实平台验证。
- 日志和附件不等于完整备份或可直接分享的导出包；导入导出及更完整备份体验按 [roadmap](../00_OVERVIEW/roadmap.md) 后续推进。
