# 工作区与本机执行设计

**日期**：2026-10-20

**模块**：`apps/daemon/src/workspaces`、`packages/agent-runtime`、`packages/execution`、`apps/desktop`

**实现锚点**：`WorkspaceService`、`ToolRuntime`、`ModelApprovalReviewer`、`resolveWorkspaceRoot`、`executeTool`、`collectShellProcess`

**状态**：已实现；macOS 本机自动化已有验证，Windows Shell 与浏览器新增目录按用户决定暂缓。

---

## 要解决什么问题

桌面 Agent 可以操作本机目录，但页面中的“选择工作区”本身不能证明后续任何路径和命令都安全。目录可能消失、变成链接，文件可能被其他程序更新；用户批准一次操作，也不代表模型可以无限扩大执行范围。

这里需要解决四个问题：

1. **工作范围可定位**：工作区关联一个已经存在的真实目录，而不是依赖 daemon 的启动目录。
2. **操作意图可确认**：工具执行前保存具体参数及审批结果，审批不能被工具输出或文件内容替代。
3. **执行范围可检查**：文件工具逐次检查真实路径，Shell 使用明确策略、环境和资源限制。
4. **取消后资源可收束**：停止 Run 必须传递到等待审批、网络和子进程，不能只让页面结束 loading。

**核心思路**：daemon 负责注册和解析工作区，Session 固定工作区关联，Run 冻结接受时的配置；ToolRuntime 保存意图、执行当前审批策略，再调用不拥有 Agent 或审批的 execution。文件检查、Plan 限制和 OS 沙箱分别承担各自职责。

**核心特点**：

- 工作区登记不复制文件，移除只归档元数据。
- 请求批准、独立 AI 复核和完全访问是显式策略，不因执行失败自动升级。
- 路径检查在注册和每次执行重复进行，写入还核对预像 hash。
- macOS Shell 使用 Seatbelt 或用户明确选择的宿主访问；两者共用取消和回收机制。

## 一、整体架构

```text
Electron Renderer / 浏览器
  │ 工作区 DTO、会话配置、工具记录
  │
  ├─ Electron 有限桥：目录选择 / 拖入目录解析
  │    └─ main 校验来源、realpath、目录类型
  │
  ▼ HTTP
WorkspaceService
  ├─ 注册：真实目录 / 保护范围检查 → SQLite 工作区配置
  └─ 使用：requireAvailable() → 已保存 canonical 路径

SessionRuntime → RunExecution（接受时 Session 配置）
  └─ ToolRuntime
       ├─ 校验工具参数 → 持久化 tool.requested
       ├─ 会话工具 / Plan 限制
       ├─ 用户审批 / ModelApprovalReviewer / full-access
       └─ 重新解析工作区 → executeTool()
            ├─ 文件工具：相对路径、链接、预像、有限结果
            ├─ macOS Shell：沙箱 / 显式宿主访问
            └─ Web：公网地址检查、逐跳校验与限时
```

目录操作并不经过 Renderer 的 Node API。桌面桥只返回经过检查的目录，不开放任意读写文件、Shell 或动态 IPC channel；浏览器通过相同 HTTP 协议使用已注册工作区。

进程和包的依赖方向见 [系统架构](系统架构设计.md)，Run 生命周期见 [Agent 运行时](Agent-Runtime.md)。

## 二、状态来源与冻结时机

| 状态                                       | 所有者                                    | 生效方式                              |
| ------------------------------------------ | ----------------------------------------- | ------------------------------------- |
| 工作区名称、图标、canonical root、revision | SQLite 工作区配置                         | 注册及带 revision 的名称/图标更新     |
| 会话的工作区 ID                            | Session 日志事实及查询投影                | 创建时确定，现有 patch 不支持改工作区 |
| 会话模型和审批模式                         | Session 日志事实及查询投影                | 后续 Run 读取当前配置                 |
| 当前 Run 的配置                            | `RunExecution.options.session` 及接受记录 | 接受时冻结，不随页面选择改变          |
| 待批准工具及决定                           | 工具事件和当前 Run 等待实例               | 一次决定只授权一个具体调用            |
| 文件当前内容                               | 工作区实际文件                            | 每次读写检查，不能以聊天历史代替      |
| 子进程与取消信号                           | 当前 Run / execution collector            | 活动执行拥有，重启不恢复进程          |

这里冻结的是接受时的模型、思考等级、工作区关联和审批策略；Plan 审核等分支工作状态仍可通过受控交互在同一 Run 内变化。冻结 Run 配置不等于缓存工作区可用性。执行仍会通过 `requireAvailable()` 和 `canonicalWorkspace()` 重新检查保存的根路径；不能因 Run 已接受而使用一个后来改变的别名。

## 三、工作区注册与使用

### 3.1 从桌面选择到注册

```text
点击居中的添加按钮，或拖入一个本机目录
  → preload 的明确目录能力
  → main 校验主 frame、所属 WebContents、可信页面及参数
  → resolveWorkspaceDirectory()：绝对路径、realpath、目录类型
  → Web 提交名称、图标和目录
  → WorkspaceService.create()
  → resolveWorkspaceRoot()：可读性和保护范围检查
  → 持久化 canonical root 与初始 revision
```

main 的目录检查解决桌面选择是否有效，daemon 的检查解决能否作为 Agent 工作区，二者不相互替代。目录选择不会把内容上传到远端或复制进应用存储。

浏览器文件选择器无法提供 Agent 所需的本机绝对路径，因此当前新增工作区要求 Electron。浏览器仍能查看和使用已有工作区；由本机服务提供目录浏览的能力尚未实现。

### 3.2 注册的目录不可直接迁移

名称和图标更新采用 `expectedRevision`，冲突时拒绝旧写入；更新 schema 没有 `rootPath`，现有工作区不能通过编辑弹窗或 API 改根目录。

Session 创建时核对工作区可用性，并固定其 ID；Session patch 同样不含 `workspaceId`。更换工作范围应注册新的工作区并创建会话，不把旧对话重新解释为另一个磁盘目录。

移除工作区只归档配置；存在未归档会话引用时拒绝移除。会话归档保留历史，工作区移除不会删除实际文件。数据所有权见 [会话存储](会话存储与恢复设计.md)。

### 3.3 根目录的实际保证

注册允许目录别名，保存 `realpath` 结果。使用时再次解析，并要求结果仍等于保存路径；原根被替换为指向其他位置的符号链接时拒绝执行。

当前没有将工作区根 inode 持久化。真实路径比较不能证明同一路径下的目录始终是原 inode，也不能防御同用户恶意进程并发替换目录；不能把“canonical 路径一致”扩大解释为文件系统快照或完整目录隔离。

## 四、文件路径与写入机制

### 4.1 根目录策略

`resolveWorkspaceRoot()` 要求绝对路径、存在且可读的目录，拒绝系统根、用户 Home 及其祖先、profile 的祖先或子目录，以及位于敏感命名目录中的根。

普通项目子目录可以使用；`.workspace` 没有被排除。应用日志所在 `.my-pi-harness` 是受保护目录，即使项目父目录被注册，也不能通过普通文件工具或默认沙箱 Shell 读写日志。

### 4.2 模型路径统一为相对路径

文件工具只接收工作区相对路径和正斜杠分隔。`parseWorkspaceRelativePath()` 拒绝绝对路径、盘符、反斜杠、`..`、敏感名称和跨平台歧义名称。

敏感名称包含 `.env*`、`.ssh`、`.aws`、`.gnupg`、`.kube`、`.npmrc`、`.netrc`、`.git-credentials`、`.git` 和 `.my-pi-harness`，不区分大小写。列表和搜索会略过这些条目及符号链接。

跨平台名称检查在当前主机上也生效，例如 Windows 设备名、ADS 冒号、控制字符和尾点/尾空格均拒绝。它保证模型路径表达一致，但不代替 Windows 原生文件系统验证。

### 4.3 执行前逐组件核对

`workspacePath()` 逐组件 `lstat`，拒绝符号链接并检查中间目录类型，再用 `realpath` 和相对路径关系核对包含范围。新建只允许最终文件缺失，父目录必须已存在。

读取通过 `openRegular()` 检查普通文件、单硬链接、`O_NOFOLLOW` 和打开前后的 inode，再有界读取；读取期间发生可观察内容变化时明确失败。

### 4.4 写入用预像约束

```text
read_file → 返回内容和 SHA-256
  → 模型提出 write_file / edit_file，携带 expectedHash
  → 审批与路径检查
  → 核对当前文件 hash
  → 计算有限 diff，写同目录临时文件并 sync
  → 再核对路径、父目录 inode 与当前预像
  → 原文件替换；新文件使用排他链接发布
```

`expectedHash:null` 只允许新建；已有文件必须匹配读取时的 hash。精确编辑默认只接受一个匹配，避免意外替换多处；内容或 diff 超过界限时拒绝执行。

文件工具的检查能发现常见竞争，但 Node 当前实现没有完整 `openat` 目录句柄操作，父目录检查与最终发布间仍有竞态。文件工具不提供针对同用户恶意并发修改的完整 OS 隔离。

## 五、一次工具调用的审批过程

### 5.1 先记录意图

`ToolRuntime` 以 Run、assistant 消息 ID 和模型 call ID 生成工具记录 ID，冻结参数并提交 `tool.requested`。参数必须符合工具 schema；调用数、参数和输出都有界限。

`describeTool()` 只解释参数，不读取文件或发起连接。文件变更、Shell 和 Web 请求需要审批；执行仍会在入口重新校验参数，审批不是校验的替代。

### 5.2 三种用户策略

| 策略                   | 需要批准的调用如何处理                                 | Shell 策略                     |
| ---------------------- | ------------------------------------------------------ | ------------------------------ |
| 请求批准 `ask`         | 等待当前调用的用户允许或拒绝                           | macOS Seatbelt                 |
| 帮我批准 `auto`        | 独立无工具模型复核，明确允许才执行；不确定或失败转人工 | macOS Seatbelt                 |
| 完全访问 `full-access` | 记录用户明确选择的允许来源                             | macOS 宿主用户权限，无 OS 沙箱 |

独立 AI 复核使用记录的用户请求、冻结规则和具体工具调用，并携带已保存计划、摘要及已答问题；它不能调用工具或改变权限。模型输出、文件、计划和命令解释不构成新的授权。复核输出经过 `allow / deny / ask` schema 校验。

复核请求的私有上下文先记录，决定、理由和来源持久化；超时、预算不足、解析失败或服务不可用转人工，不能自动切换到完全访问。Run 取消则终止复核，不能把取消处理成允许。

人工审批只对应当前工具 ID，结束、过期或不属于当前 Session 的决定被拒绝。等待有超时和取消处理；批准后再次检查 AbortSignal、工作区和实际文件目标。

### 5.3 Plan 与会话工具

Plan 模式在调用执行包前拒绝具有副作用的工具，完全访问也不能绕过。会话中的计划、任务、提问、历史检索和上下文操作由 `SESSION_TOOL_DEFINITIONS` 提供，不要求选择工作区。

实现还保留内部 `read-only` 审批模式，可拒绝文件变更、Shell 和 POST；它不是当前面板的第四个选项。Plan 是工作模式，与审批模式分别判断，不将“计划审核通过”解释为未来全部操作获批。

## 六、macOS Shell 的两种执行方式

### 6.1 默认沙箱

ask 和 auto 使用 `/usr/bin/sandbox-exec` 启动 `/bin/bash --noprofile --norc -c`。Seatbelt 从 deny-default 开始，只开放工作区、独占临时目录和明确系统/运行时工具链的读取，写入限于工作区和临时目录，网络不开放。

profile、秘密文件和 `.my-pi-harness` 的读写明确拒绝；`.git`允许读取、禁止写入，与文件工具拒绝访问`.git`的策略不同。部分系统元数据和根目录枚举用于启动系统程序。沙箱不可用或启动失败直接报错，不回退宿主执行。

### 6.2 完全访问

full-access 在 macOS 直接启动同一个 bash，以宿主用户权限运行，使用真实 Home，不提供 OS 层面的工作区外文件或网络限制，也不执行系统提权。

此策略仍要求合法的已注册 cwd，仍执行工具参数、Plan、取消、时间及输出限制。文件工具本身的工作区保护规则不变；“完全访问”扩大的是 Shell 的宿主访问能力。

两种策略都使用独占 TMPDIR 和环境白名单，不继承宿主全部环境、模型凭据、SSH socket、代理、`NODE_OPTIONS` 或 `BASH_ENV`。命令作为 bash 的明确参数传入，spawn 本身不启用额外宿主 shell。

### 6.3 取消和进程回收

```text
Run AbortSignal / 总时限 / 输出超限 / 流错误 / leader 退出
  → collector 开始收束
  → TERM 自有 POSIX 进程组
  → 有界检查，仍存活则 KILL
  → 确认所属组没有存活成员
  → 等待 stdout / stderr 和 child close
  → 清理独占临时目录
  → 生成成功或明确失败结果
```

leader 的 `exit` 不是执行成功的充分条件。最终输出可能还在管道中；UTF-8 跨 chunk 分别解码，退出后的流错误、取消和输出超限仍应返回失败。

回收不能确认、输出管道不关闭或临时目录清理失败时，明确报告清理失败，不返回部分成功。回收只针对自有进程组，不按进程名误杀；主动 `setsid/setpgid` 脱离组的后代不在保证内。

Shell 当前只实现 macOS；Windows 和 Linux 在两种策略下都返回 `SANDBOX_UNAVAILABLE`。模拟分支拒绝测试不等于真实 Windows 执行与进程回收验证。

## 七、网络与外部副作用

`web_fetch` 不使用 Shell 的网络能力。它通过单独的确定工具执行公网 HTTP(S)，检查 DNS 的全部地址并将实际 socket 绑定已核对地址；重定向每跳重查，不继承 cookies、认证头或环境代理。

请求限制协议、端口、总时间、跳转次数及响应大小，拒绝私网、回环、元数据地址、HTTPS 降级、压缩和不支持的内容。POST 要求审批且不因结果未知自动重试。

虽然实现的 Web 访问不依赖磁盘根，当前 ToolRuntime 只在 Session 有工作区时装配这组执行工具；没有工作区时不会通过页面选择隐式使用进程目录。

执行状态和工具结果持久化后再向页面发布。daemon重启保留未派发调用的interrupted和MCP屏障后的unknown事实，不重跑命令；无法取得终态不证明外部副作用未发生。

### 7.1 本地MCP持久进程

`startPersistentProcess`拥有明确程序/参数、真实工作根、冻结隔离、白名单环境以及受监管的stdin/stdout/stderr；integrations通过有限write/close接口收发SDK字节，不持有ChildProcess。观察器在spawn前装好，实际写入前再次检查取消，关闭等待所属进程组、leader、所有管道与临时目录结算，不以leader退出当作完成。

官方Client负责JSON-RPC校验和配对；自有Transport补严格有界LF分帧、UTF-8、输出速率和一次写许可。目录发现和调用分别取得租约，最后租约释放关闭连接，目录缓存不保活进程。强制回收共享连接会影响其余未完成调用，已派发者逐项结算unknown；清理失败保留资源责任并阻止普通配置变更，最终关闭继续报告失败。

启动信任只授权程序、入口身份、参数、根、环境和隔离范围，工具调用仍经过原审批。受监管隔离与完全访问分别授权，不能自动降级；Plan与内部read-only不提供外部工具。秘密字节只注入明确授权的子进程，已知秘密的直接回显在进入目录、模型结果和诊断前过滤或拒绝。字段、权限撤销与首版范围见[本地MCP协议](../03_API/local-mcp.md)。

## 九、边界与后续衔接

- 工作区是显式登记的访问根，不是容器、虚拟机或完整文件快照；检查点恢复不撤销文件或命令效果。
- 当前本地MCP stdio仅支持macOS；远端HTTP、MCP OAuth、动态工具加载与Skills已接入，授权和失败语义见[能力扩展设计](能力扩展与授权设计.md)，真实账号及目标平台按所属验收记录确认。根目录迁移、浏览器新增目录、Windows Shell与Computer Use尚未实现。
- 完全访问降低 Shell 隔离，仅由用户选择；独立复核和默认沙箱都不以失败为由升级权限。
- Web 抓取、PDF worker 和文件工具各有资源及输入限制，不能把其中一种隔离机制宣称为其他能力的 OS 安全保证。
- 平台与后续扩展范围以 [roadmap](../00_OVERVIEW/roadmap.md) 为准；执行策略硬约束由 [后端规范](../05_CONSTRAINTS/backend.md) 维护。

## 十、验收要点
